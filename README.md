# AI 智能客服 MVP（P0 完整版）

按《AI智能客服MVP功能需求清单》的 **P0 清单（7 模块 22 个功能点）** 实现的可运行、可演示系统。

- 后端：Python 3.10+ / FastAPI
- 存储：SQLite（零外部依赖，首次启动自动建库并导入 33 条种子知识库）
- 对话：**双通道检索** —— 词面混合检索（字符 n-gram + 同义词典 + 关键词）+ **Embedding 向量召回**
- 实时：**WebSocket 实时推送**（失败自动降级为轮询）
- 前端：5 个原生 HTML 页面（用户会话页 / 客服工作台 / 数据看板 / 运营后台 / 登录页），无构建步骤

> 全部能力**离线可用**：向量召回默认走内置的「同义词图向量」，不需要 numpy / torch / 模型下载 / 外部向量库。

### 推荐演示动线（5 分钟看完 P0 全貌）

1. **用户页**：输入「我想退货，怎么操作」→ 得到退货流程
2. 接着输入「那运费谁出呢」→ 机器人**先澄清退货原因**（槽位澄清）
3. 点「商品质量问题」→ 给出**质量问题的精准答案**（而不是笼统回答）
4. 输入「钱什么时候回来」→ **向量召回命中《退款多久能到账？》**（纯词面检索这句会兜底）
5. 输入「你们太差了，我要投诉」→ **规则触发转人工**并自动分配客服
6. **客服工作台**（新标签页）：看到排队/接待中的会话 → 点「接入会话」→ 右侧看到**携带意图、槽位、触发原因的上下文摘要** → 回复用户
7. 回用户页 → **客服消息实时出现（WebSocket 推送，无轮询延迟）** → 点「结束会话」→ 提交评价
8. **运营后台** → 会话记录 → 查看该会话的完整消息流、**答案溯源**、转人工记录、评价
   → 「机器人设置」页签底部：**向量召回面板**，用「对照测试」并排对比词面 vs 向量的召回差异
9. **数据看板** → 看到独立解决率、转人工率、TOP 未解决问题

## 4. 多轮上下文与槽位澄清（M2-3）

不依赖大模型记忆，而是**显式维护会话状态**，保证可解释、可调试。

### 4.1 上下文改写

`chat_session` 表记录 `last_question`（上一轮命中的标准问）、`last_category`、`slots`、`fallback_count`、`clarify_round`。

当消息很短（≤6 字）或含指代词（「那…呢」「它」「这个」「还有呢」）时判定为**依赖上文的追问**，随后：

1. 用「上一轮标准问 + 当前消息」拼接后**重新检索**
2. 把检索范围**限定在上一话题的分类内**
3. **排除已经答过的条目**（避免重复回答同一问题）
4. 若排除后没有好结果，则**允许再次命中上一轮条目**（追问更可能指回当前话题）
5. 话题已知时判定阈值放宽 20%（`MID_CONFIDENCE × 0.8`）

### 4.2 槽位澄清

知识条目可配置一个 `slot` 字段，表示"这条答案取决于某个前提"。命中该条目时机器人**不会直接回答**，而是先追问：

```
用户：那运费谁出呢
机器人：为了给您准确的答复，请问这次退货的原因是？
        [商品质量问题] [个人原因（不喜欢 / 拍错）] [七天无理由]
用户：商品质量问题
机器人：（已记录：退货原因 = 商品质量问题）
        因商品质量问题导致的退货，寄回运费由我们全额承担…
```

机制要点：

- 槽位规则定义在 `config.SLOT_RULES`（3 组内置：退货原因 / 会员等级 / 发票类型）
- **一轮只问一个问题**，槽位回答后做**二次检索**落到细分条目上
- 澄清轮次上限 3 轮（可配），超出则触发转人工
- 用户中途换话题 → 放弃当前槽位收集，按新意图重新路由
- 槽位值记录在会话里，**同步给人工客服**作为上下文

三条经过实测打磨的关键规则（都是踩过坑之后加的）：

| 规则 | 为什么需要 |
|---|---|
| **判断依据是「用户原话」而不是命中的条目** | 引入向量后，「那运费谁出呢」会命中细分条目《商品质量问题退货的运费》。若按条目判断，就会以为前提已明确而直接给出"质量问题"的答案。按用户原话判断，才会正确地反问 |
| 用户已经说了前提 → 不再追问 | 「商品质量问题退货的运费谁承担」「七天无理由退货的运费谁出」都应直接作答；只有泛化的「运费谁出」才需要澄清 |
| 二次检索时区分「泛化入口」与「细分条目」 | 泛化入口（自身带 `slot`，如《怎么开发票》）必须排除，否则会又答回泛化条目；细分条目（不带 `slot`，只是恰好排第一）要放回来，否则会答到别的条目上 |

实测 6 组场景全部落在正确的细分条目上：

```
我想退货，怎么操作 → 那运费谁出呢 → 商品质量问题   ⇒《商品质量问题退货的运费由谁承担？》
退货运费谁承担    → 个人原因                    ⇒《个人原因退货的运费由谁承担？》
退货运费谁出      → 七天无理由                   ⇒《七天无理由退货的运费由谁承担？》
会员有哪些权益    → 黑卡                       ⇒《黑卡会员有哪些权益？》
怎么开发票       → 专票                       ⇒《增值税专用发票怎么开？》
怎么开发票       → 电子发票                    ⇒《电子普通发票怎么开？》
```

## 5. 转人工机制（M4）

### 5.1 五类触发规则（后台可调阈值）

| 规则 | 默认阈值 | 说明 |
|---|---|---|
| 高风险关键词 | 1 | 投诉、曝光、起诉、12315、媒体、法院 等 → **强制**转人工 |
| 负面情绪词 | 2 | 生气、骗子、垃圾、差评、无语 等 |
| 连续兜底次数 | 2 | 连续 N 次没匹配到答案 → 主动转人工，不等用户点 |
| 会话轮次上限 | 15 | 超过 N 轮仍未解决 |
| 澄清轮次上限 | 3 | 连续澄清超过 N 轮仍无法作答 |

### 5.2 排队与分配

```
触发转人工
  ├─ 人工在线（服务时段内 且 有在线客服）
  │    ├─ 有空闲客服 → 空闲优先自动分配，客服工作台立刻出现该会话
  │    └─ 全部满载   → 进入排队，用户看到「当前排在第 N 位」
  └─ 人工离线 / 无人在线 → 提示服务时段与留言，**不会无声失败**
```

- 客服接待上限 `max_concurrent`（默认 3），超出时接口返回明确提示，不会无限接单
- 排队时长、分配时长、客服首次响应时长均被记录并进入看板

### 5.3 上下文同步（M4-3）

客服点击接入后，工作台右侧立即展示摘要卡片：会话 ID、访客标识、当前状态、轮次与兜底次数、
**已识别意图**、**已收集槽位**、**转人工触发原因与详情**、**引用过的知识条目**。

> 细节处理：若机器人尚未命中任何条目就被高风险词直接转接，摘要会用客户的第一句话作为意图，
> 避免客服端看到「未识别」。

### 5.4 人工接待期间机器人静默

会话进入人工接待状态后，用户消息只入库、不回话（接口返回 `answer_type=waiting_agent` 且回复为空），
消息实时同步到客服工作台。结束时系统按口径**自动归因**：`resolved_by = bot / agent / unresolved`。

## 6. 检索原理与阈值调参

### 打分公式

```
score = 0.68 × text_sim + 0.32 × keyword_score
text_sim = 0.65 × 二元组Dice + 0.35 × 一元组Dice   （在标准问与全部相似问中取最大值）
keyword_score = min(1, 命中关键词数 / min(关键词总数, 3))
```

四条补充规则：

1. **精确命中短路**：标准问 / 相似问与用户问题互为子串 → 直接 0.97
2. **同义词扩展**：内置 18 组同义词（退货/退换、退款/退钱、物流/快递、发货/发出…），
   只用于**文本相似度**，不参与精确命中与关键词计数（否则「多少钱可以免费上门取件」会因扩展出「价格」而误命中收费类条目）
3. **文档切片**：导入的文档切片额外把正文作为匹配面，否则自动生成的标题几乎无法被召回
4. **关键词零命中折扣**：条目配了关键词、但用户原话里一个都没出现时，`text_sim` 乘
   「的/是/怎么」这类功能词二元组蹭到高分（实测「今天天气怎么样」曾命中「汽车配件类商品…」），
   这条规则把域外问题的**直接作答**误命中从 1/10 降到 0/10，且不影响 26/26 的电商召回自测。

### 置信度分档

| 分数区间 | 行为 |
|---|---|
| ≥ `KB_HIGH_CONFIDENCE`（默认 0.52） | 直接作答 |
| ≥ `KB_MID_CONFIDENCE`（默认 0.30） | 作答 + 主动确认「您是想问…吗」 |
| < `KB_MID_CONFIDENCE` | 不生成答案，进入兜底「猜你想问」 |

### 环境变量

| 变量 | 默认 | 说明 |
|---|---|---|
| `KB_HIGH_CONFIDENCE` | 0.52 | 直接作答阈值 |
| `KB_MID_CONFIDENCE` | 0.30 | 兜底分界阈值 |
| `KB_TOP_K` | 3 | 返回候选数 |
| `SESSION_TIMEOUT_SECONDS` | 600 | 无消息自动结束会话 |
| `QUEUE_WARN_SECONDS` | 60 | 排队超时提示阈值 |
| `CHUNK_MIN_CHARS` / `CHUNK_MAX_CHARS` | 200 / 600 | 文档切片长度 |
| `EMBEDDING_PROVIDER` | auto | 向量召回 provider：`auto` / `local` / `api` / `off` |
| `EMBEDDING_API_KEY` | 空 | 在线语义向量的 Key（配置后 `auto` 自动切到 `api`） |
| `EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` | DeepSeek / BAAI/bge-m3 | 在线 Embedding 接口 |
| `VECTOR_WEIGHT` / `VECTOR_MIN_COSINE` / `VECTOR_AGREE_BONUS` | 0.82 / 0.55 / 0.06 | 向量融合权重（已实测标定） |
| `VECTOR_ONLY_REQUIRE_CONFIRM` | 1 | 仅靠向量命中时是否强制先向用户确认 |
| `WS_ENABLED` | 1 | 是否启用 WebSocket 实时推送 |
| `WS_HEARTBEAT_SECONDS` | 25 | 服务端心跳间隔 |
| `AUTH_ENABLED` | 0 | 是否启用四角色权限 |

## 7. 向量召回（Embedding）

纯词面检索的天花板是「没有字面重叠就召回不到」。例如「钱什么时候回来」「登不上去了」
「贵不贵」这类口语化表达，与知识库里的「退款多久能到账」「忘记密码怎么办」「产品怎么收费」
几乎不共享字符，词面分只有 0.2~0.4，会直接掉进兜底。

本版本接入 Embedding 向量召回解决这个问题，同时**保持零依赖、可离线运行**。

### 7.1 两种 Provider（可插拔）

| Provider | 说明 | 是否需要外部服务 | 能力边界 |
|---|---|---|---|
| `local`（默认） | **离线同义词图向量**：以同义词典 + 词项共现构建词项向量，文档/查询表示为词项向量的加权和（稀疏向量，纯 Python，无 numpy / torch / 模型文件） | ❌ 完全离线 | 能理解**同义词典覆盖到**的说法（钱→退款、登不上→密码、坏了→保修）；没有开放域世界知识 |
| `api` | **在线语义向量**：调用 OpenAI 兼容的 `/embeddings` 接口（如 BGE-M3） | ✅ 需 `EMBEDDING_API_KEY` | 真正的语义理解，能覆盖词典未收录的表达 |
| `off` | 关闭向量召回，退化为纯词面检索（保留作为对照与兜底） | ❌ | — |

`EMBEDDING_PROVIDER=auto`（默认）会在配置了 Key 时自动用 `api`，否则用 `local`。
**任何 provider 出错都会静默降级为纯词面检索，绝不影响问答可用性。**

### 7.2 离线 provider 是怎么工作的

它本质是一个**微型词向量模型**，只不过训练信号来自同义词典与语料共现，而不是大规模预训练：

```
词项图
  ├─ 同义词典边（强，0.9）      「退钱」—「退款」，「登不上」—「密码」
  ├─ 跨组语义边（中，0.75）     「退货流程」—「退款」，「发货」—「物流」
  └─ 文档共现边（弱，0.35×idf）  同一篇文档里共同出现的词项

词项向量 = 自身 one-hot + 邻居加权      （归一化）
文档向量 = Σ(idf × tf × 词项向量)      （归一化）
查询向量 = 同样方式构造
相似度   = 稀疏向量余弦
```

关键点是**传播**：查询里的「钱」不在知识库词表里，但它在同义词典里与「退款」相连，
于是查询向量会在「退款」这一维上获得分量，从而与退款条目产生真实的余弦相似度。

对应代码：`app/embedding.py` 的 `LocalProvider`，词项图定义在 `app/knowledge.py`
的 `SYNONYM_GROUPS`（22 组）与 `SYNONYM_LINKS`（26 条跨组边）。

### 7.3 融合打分与决策规则

```
打分（app/knowledge.py）：
    final = max( 词面分 , VECTOR_WEIGHT × 向量余弦 )
    两路都命中（词面 ≥ MID）时 + VECTOR_AGREE_BONUS
    向量余弦 < VECTOR_MIN_COSINE 视为不可信，直接忽略

决策（app/dialog.py）：
    仅靠向量命中（词面分不达标）的候选 → 强制走「作答+确认」，不允许「直接作答」
```

- 取 `max` 而不是加权平均，是为了**完整保留原有词面阈值标定**（0.52 / 0.30 继续有效）
- **打分不做封顶**：封顶会制造并列、丢失排序信息；「不给直接作答」这条策略放在决策层执行
- 阈值是**实测标定**出来的：离线向量下相关查询余弦集中在 **0.70~1.00**，无关查询在 **0.30~0.45**，
  因此 `VECTOR_MIN_COSINE=0.55` 能干净地分开两者
- 为什么必须有「仅向量必须确认」这条规则：离线稀疏向量在小语料上余弦偏乐观 ——
  实测「分数能换东西吗」（错别字）对《换货怎么操作？》余弦高达 **0.993**。
  若允许它直接作答，就是"自信地答错"；强制确认后，同一条查询会变成
  「您是想问「换货怎么操作？」吗？」——**同一个错误被转化成了安全的交互**。
  想要更强的语义能力，请切到 `api` provider

### 7.4 实测效果

`python scripts/probe_vector.py` 对 19 条口语化问法做「关闭 vs 开启向量召回」对照：

```
纯词面通过 13/19 | 融合后通过 19/19 | 改善 6 例，退化 0 例

用户问法        纯词面命中               融合后命中              词面分  向量分
钱什么时候回来    退款多久能到账？          退款多久能到账？         0.367  0.935
退钱到哪了       退款多久能到账？          退款多久能到账？         0.199  0.789  ↑改善
登不上去了       忘记密码怎么办？          忘记密码怎么办？         0.275  0.999  ↑改善
贵不贵          你们的产品怎么收费？        你们的产品怎么收费？      0.245  0.966  ↑改善
换一个行不行      换货怎么操作？           换货怎么操作？          0.290  0.955  ↑改善

```

**「改善 6 例、退化 0 例」是这个改动最重要的验收口径**：既要提升同义召回，
又不能把原本该兜底的无关问题变成乱答；同时错别字类查询虽然会被误命中，
但因为有「仅向量必须确认」的保护，只会变成一次确认而不是错误答案。

> 注意一个有意思的连带修正：向量让「那要多久」这类省略式追问在**脱离上下文**时也能拿到
> 较高分（例如误命中「发票多久能开出来」），这反而会让系统跳过上下文消歧。
> 因此 `app/dialog.py` 里对「追问」场景做了特殊处理：**追问一律走上下文聚焦检索**，
> 并在比较时给上下文话题更宽的容差（0.15 vs 0.05）。

### 7.5 索引与运维

- 向量随条目持久化在 `knowledge.embedding`（稀疏向量存 JSON，稠密向量存数组），**重启不需要重算**
- 用内容 hash 判断条目是否变化，`api` provider 走**增量嵌入**（只嵌入新增/修改的条目）
- `local` provider 的词表依赖整个知识库，任何改动触发全量重建 —— 实测 33 条约 **40 ms**，可接受
- 后台「机器人设置」页签内有**向量召回面板**：状态卡片、增量/全量重建、以及**词面 vs 向量对照测试**
- 接口：`GET /api/admin/embedding`、`POST /api/admin/embedding/rebuild`、`POST /api/admin/embedding/test`

## 8. 实时推送（WebSocket）

原先用户端每 2.5 秒、工作台每 5 秒/3 秒做一次 HTTP 轮询，最多有 3 秒延迟且空转请求多。
现在改为 WebSocket 服务端主动推送，**连接正常时前端不再有任何轮询**。

### 8.1 两条通道

| 通道 | 地址 | 用途 |
|---|---|---|
| 用户端 | `ws://<host>/ws/chat/{session_id}` | 接收客服消息、系统消息、会话状态变化、评价邀请 |
| 客服端 | `ws://<host>/ws/agent` | 接收新排队会话、会话分配、新消息、坐席状态变化 |

### 8.2 事件协议

**用户端下行**

| 事件 | 说明 |
|---|---|
| `sync` | 连接建立后立即下发；含 `status` / `messages` / `queue_position` / `clarify` |
| `message` | 新消息（`role` 为 `bot` / `agent` / `system`），含完整答案溯源 `source_details` |
| `status` | 会话状态变化（机器人接待中 / 转人工排队 / 人工接待中 / 已结束） |
| `handoff` | 转人工结果：`assigned`（是否已分配）/ `offline`（是否非服务时间）/ `queue_position` |
| `csat_request` | 会话结束时邀请评价 |
| `ping` / `pong` | 心跳保活 |

**用户端上行**：`{"type":"ping"}`、`{"type":"sync","after":<lastId>}`（增量补齐）、`{"type":"status"}`

**客服端下行**：`sync` / `message` / `session_created` / `session_updated` / `handoff` / `agent_status_changed` / `ping`

### 8.3 工程细节

- **同步下发 + 事件驱动**：连接建立先给一次全量快照，之后只推增量事件，前端不需要额外查询
- **心跳**：服务端每 `WS_HEARTBEAT_SECONDS`（默认 25s）发一次 `ping`，顺带清理死连接
- **并发写保护**：每个连接一把 `asyncio.Lock`，避免心跳广播与业务广播同时写同一个 WebSocket
- **线程模型**：路由处理器是同步函数（FastAPI 放在线程池执行），广播通过
  `asyncio.run_coroutine_threadsafe` 投递回主事件循环 —— 不需要把整条业务链路改成 async
- **断线重连**：前端指数退避重连，重连后发 `sync` 补齐断线期间消息（不丢不重）
- **降级**：连续 3 次连接失败自动切回轮询，并在 UI 上明示「已降级为轮询」，后台继续尝试重连
- **推送失败不影响业务**：所有推送都包了异常保护，消息先落库再推送，推送失败前端重连即可补齐

### 8.4 验收

```bash

```

## 9. 文档导入与自动切分（M3-2）

支持 **粘贴文本 / .txt / .md / .docx**（`.docx` 需 `pip install python-docx`；扫描版 PDF 不支持，请转文本）。

切分规则：

1. 按**标题行**与**空行**切块。标题识别同时支持 markdown `#`、数字序号，以及纯文本中的短标题行
   （独立成行、≤22 字、后面跟着正文）——这样粘贴的纯文本文档也能正确分节
2. 过短片段向后合并，但**不跨越标题边界**（否则整篇会被并成一个片段）
3. 超过 600 字的片段按句子边界切分
4. 每个片段自动生成「标准问」（取标题行）与「相似问法」（取正文前几个短句，提升召回）

导入后的流程：**先入草稿 → 人工预览 → 确认发布才参与检索**。发布前可用「召回预检」验证效果。

## 13. 知识库格式

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `question` | string | ✅ | 标准问 |
| `answer` | string | ✅ | 标准答 |
| `category` | string | | 分类；**多轮追问时会优先在同分类内检索** |
| `similar` | string[] | | 相似问法，命中即等价于标准问（0.97），**提升召回性价比最高** |
| `keywords` | string[] | | 关键词，用户原话中出现即加权 |
| `slot` | string | | 需要先澄清的槽位 ID（`return_reason` / `member_level` / `invoice_type`） |
| `enabled` | bool | | 停用后立即不再参与检索（比删除安全） |

新增方式：

```bash
# 1) 后台界面（推荐）：/admin → 知识库 → + 新增知识
# 2) 接口
curl -X POST http://127.0.0.1:8000/api/knowledge \
  -H "Content-Type: application/json" \
  -d '{"question":"怎么申请开具电子发票？","answer":"在「我的订单」中点击申请开票…",
       "category":"支付发票","similar":["电子发票怎么开"],"keywords":["电子发票","开票"],"enabled":true}'

# 3) 批量：编辑 app/seed_data.py 的 SEED_KNOWLEDGE，删除 data/ 后重启
# 4) 文档导入：/admin → 文档导入（粘贴或上传，预览后发布）
```

> `similar` 是提升召回性价比最高的字段（命中即 0.97）。扩充知识库时优先做的事就是
> **把真实用户的问法补成 `similar`**，而不是不断新增标准问 —— 后者会让近义条目互相抢分。
> 但要注意：**跨品类通用的问法（「质量怎么样？」）不能当 similar**，否则会精确命中短路，

**「怎么知道是不是命中了」的三种答法**：

| 你的处境 | 能算的指标 | 怎么做 |
|---|---|---|
| 还没有真实数据 | **自召回率**（每条知识能否被自己的问法召回） | `--selfcheck`：用条目的标准问 + 相似问法当测试集 |

| 已经上线跑了一段 | **命中变化**（改动前后对比） | `--from-sessions`：回放真实提问，看 ≠ 的条目是变好还是变差 |

自检报告实测样例（就是靠它发现了一个真实 bug，见下）：

```
条目 33 条 | 测试问法 157 条 | 自召回率 100.0% (157/157)
完全可自召回条目：33/33
```

**怎么读自检报告**：

- **自召回率低** → 这条知识在线上很可能答不上（问法覆盖不够，补 `similar` / `keywords`）
- **串到了另一条** → 两条知识语义重叠，是误命中的高发点（合并，或删掉过于泛化的那条）

> **它抓到过一个真实 bug**：修复前自召回率是 94.9%（28/33），因为泛化条目靠"子串"抢占了细分条目 ——
> 问「商品质量问题退货的运费由谁承担」会命中泛化的「退货的运费由谁承担」。
> 根因有两层：① 精确命中不区分「用户问得更具体」和「条目问得更具体」；
> ② 一致加成把多个候选一起顶到 1.0，排序被抹平后按 id 顺序决出胜者。
> 修完自召回率 100%，且 8 组槽位/前提场景全部落在正确条目上。
> **这类问题光靠手工点几下是发现不了的** —— 它只在"问法和标准问高度重叠"时暴露。

## 15. 技术栈与设计取舍

| 选择 | 原因 |
|---|---|
| FastAPI | 轻量、自带 Swagger、类型校验；路由按用户/客服/运营/认证分组 |
| SQLite（标准库 `sqlite3`） | 零外部依赖；每次操作短连接，**天然保证「后台改完立即生效」**，不需要缓存失效逻辑；向量直接存表里，不需要独立向量库 |
| 词面检索 + 向量召回双通道 | 词面分**可解释**（能看到命中的问法）；向量分补足同义表达；两者取 max 融合，既提升召回又不破坏原有阈值标定 |
| 离线同义词图向量作为默认 provider | 不引入 numpy / torch / 模型下载，**保持「克隆下来就能跑」**；同时把接口留成可插拔，需要更强语义时一个环境变量切到在线 Embedding |
| 显式会话状态而非大模型记忆 | 可解释、可调试、可同步给人工客服；不依赖外部服务 |
| WebSocket 主通道 + 轮询降级 | 实时推送消除 2–3 秒延迟与空转请求；但企业网络/代理对 WS 不友好，因此保留降级路径，宁可慢也不断 |
| 推送用 `run_coroutine_threadsafe` 桥接 | 业务链路保持同步写法（易读、易测），只有广播这一层跨到事件循环，不必整链改 async |
| 13 张表 + 自动迁移 | 老库自动补列（`PRAGMA table_info` + `ALTER TABLE`），升级不用删库 |
| 大模型仅做润色 | 生成与决策分离，从架构上规避幻觉 |

### 配置了别的方案而非硬编码

`config.SLOT_RULES`（槽位规则）、`config.DEFAULT_TRIGGER_RULES`（触发规则）、
`config.SENTIMENT_WORDS` / `RISKY_WORDS`（词表）、`config.DEFAULT_BOT_CONFIG`（全部话术）
都集中在 `app/config.py`，其中触发规则与话术可在后台在线调整。

## 16. 已知限制（诚实说明）

1. **离线向量没有开放域世界知识**。它靠同义词典与共现传播工作，词典没覆盖的说法
   （例如「分期免息怎么算」）仍然召回不到。想覆盖这类表达，请配置 `EMBEDDING_API_KEY`
   切到在线语义向量 —— 这是**唯一**能真正解决开放域同义理解的方式，实测差异明显。
2. **在线向量 provider 在本环境未被实测**（没有可用的 Embedding API Key）。
   代码路径、批处理、增量索引、失败降级都已实现，但**「API provider 的真实召回效果」这一项没有实测数据**，
   接入真实 Key 后建议用 `python scripts/probe_vector.py --api` 自行验证。
3. **不支持 PDF（含扫描件）与 .doc 老格式**，需先转文本；`.docx` 需要额外安装 `python-docx`。
4. **WebSocket 为单进程内存态**：连接注册表在进程内，多实例部署需要 Redis Pub/Sub 之类的广播层，
   否则不同实例上的客服与用户互相收不到消息。当前实现适合单实例演示。
5. **没有做消息可靠投递**：推送失败依赖前端重连后重新同步；未实现 ACK 与重发队列。
6. **客服工作台不支持"客服主动转接给其他客服"**（PRD 未要求），也不做会话转交记录。
7. **看板为实时聚合**，数据量大（数十万会话）时需改为 T+1 物化表 + 分区。
8. **权限为演示级实现**：Token 无状态、无刷新机制、无登录失败锁定；密码使用 PBKDF2 + 随机盐存储。
9. **不做多租户/多业务线隔离**，数据表未预留 `tenant_id`。
10. **超时扫描为进程内定时任务**（每 60 秒），多实例部署需改为外部调度。
11. 会话数据默认长期留存，未实现按合规要求的自动归档与清理。

## 17. 常见问题

**Q：启动报 `ModuleNotFoundError: No module named 'fastapi'`**
A：`pip install -r requirements.txt`（含 `python-multipart`，用于文件上传）。

**Q：文档上传 .docx 失败**
A：安装 `pip install python-docx`，或改用粘贴文本 / .txt / .md。

**Q：改了知识库，机器人还答旧的**
A：正常情况下不会（检索每次都直接读数据库）。请检查：① 该条目是否被停用；
② 是否被其他**分数更高**的条目抢占（用后台「检索测试」看候选排序）。

**Q：机器人总说「您是想问…吗」**
A：这是中等置信度的保护性确认。把 `KB_HIGH_CONFIDENCE` 调低（如 0.35）会更多走直接作答。

**Q：转人工后没人接**
A：检查是否有客服处于「在线」状态（工作台右上角状态选择），以及当前时间是否在服务时段内
（后台「机器人设置」可改）。两者任一不满足都会走离线提示。

**Q：想清空所有数据重新演示**
A：删除 `data/` 目录后重启即可（知识库会重新导入种子数据）。

**Q：同一台机器能同时跑演示模式和权限模式吗**
A：可以，用不同的库文件：`APP_DB_PATH=data/app_auth.db AUTH_ENABLED=1 python run.py --port 8030`。

**Q：能接入真实大模型吗**
A：

```bash
# Windows
$env:LLM_API_KEY="sk-xxxx"; $env:LLM_BASE_URL="https://api.deepseek.com/v1"; $env:LLM_MODEL="deepseek-chat"
python run.py
```

配置后大模型只负责把**已命中知识库的答案**组织得更自然，命中与否仍由检索分数决定 ——
从架构上避免幻觉。调用失败会自动回退到知识库原文，不影响可用性。

**Q：为什么「钱什么时候回来」现在能答上来了，之前不行**
A：这是向量召回的效果。默认的离线 provider 通过同义词典把「钱」和「退款」连了起来，
所以能命中《退款多久能到账？》。想验证：后台「机器人设置」→ 向量召回面板 → 对照测试，
能并排看到「纯词面」与「词面+向量」两种结果。

**Q：用户说的一句话词典没覆盖，还是答不上来怎么办**
A：两种做法：① 在 `app/knowledge.py` 的 `SYNONYM_GROUPS` 里补一组同义词（**零成本、立即生效**，
适合领域词）；② 配置 `EMBEDDING_API_KEY` 启用在线语义向量（适合开放域口语表达）。
前者可控，后者覆盖面广。

**Q：怎么确认前端真的用的是 WebSocket 而不是轮询**
A：打开浏览器开发者工具 → Network → WS，能看到 `/ws/chat/<会话ID>` 或 `/ws/agent` 的长连接；
页面顶栏也有「实时」绿点 / 「轮询」灰点的状态标识。另外 Network 里**不应**再有
2.5 秒 / 3 秒周期的 `/messages?after=` 请求。

**Q：WebSocket 连不上（公司代理拦截）**
A：前端会自动降级为轮询并在顶栏提示「已降级为轮询」，功能不受影响。
也可以直接用 `WS_ENABLED=0 python run.py` 从服务端关闭实时通道。

**Q：怎么知道机器人是不是真的「命中」了知识库**
A：页面上就能看：用户页每条回复下方有 `相似度 0.83（词面 0.37 / 语义 0.93）` 和「来源：#16 退款多久能到账？」；
后台「知识库 → 检索测试」能逐句看候选与分数；「会话记录」里每条机器人消息都带溯源。
想系统性评估，用 `python scripts/eval_retrieval.py`（自检 / 批量问法 / 真实会话回放三种模式，见第 14 节）。

**Q：现在知识库只有 33 条种子数据，我怎么知道换成真实知识后还能不能命中**
A：跑 `python scripts/eval_retrieval.py --selfcheck`。它不需要真实数据，用知识库自身
「标准问 + 相似问法」当测试集，**自召回率低或互相抢占的条目就是线上会出问题的地方**，
报告会直接指出是哪条、被谁抢走了。换成你的真实知识后重跑一次即可。

**Q：怎么给知识库补充内容**
A：三条路：① 后台「文档导入」上传 .txt/.md/.docx，切分预览后发布（推荐）；
② 编辑 `app/seed_data.py` 的 `SEED_KNOWLEDGE` 后重启；③ 调 `POST /api/knowledge` 批量写入。
补完之后**务必**跑一次 `python scripts/eval_retrieval.py --selfcheck`（看新条目是否互相抢占）
与 `python scripts/probe_vector.py`（看有没有引入退化）。

**Q：加完数据后机器人开始乱答不相干的问题怎么办**
A：这是扩充知识库最常见的副作用，按顺序排查：
① 用后台「检索测试」看误命中条目的分数构成，确认是词面分还是向量分把它抬上来的；
② 检查新条目是否有**跨品类通用相似问法**（「质量怎么样？」「有优惠吗？」），有就删掉——
相似问命中会走精确匹配短路（0.97），杀伤力最大；
③ 检查新条目的 `keywords` 是否是**正文里真实存在的词**，不真实的关键词会造成假命中；
④ 必要时上调 `KB_HIGH_CONFIDENCE`（如 0.58）或 `VECTOR_MIN_COSINE`（如 0.62），
每次调整后同时跑 `probe_scores.py`（别伤召回）与 `probe_vector.py`（别引入退化）。
